# Технічна специфікація проєкту — довідник для побудови нового сайту

## Як користуватись цим документом

Це повний опис архітектури вже побудованого сайту (рекрутингова агенція TARALEX GRUP). Надішли цей файл в новому чаті з проханням: **"Побудуй схожий сайт з нуля на Docker, за цією ж архітектурою, але з іншими даними (дам окремо) і на іншому домені"**.

Документ описує СТРУКТУРУ й ПІДХІД — не конкретний бізнес-контент. Свої дані (назву компанії, кольори, тексти, домен) вкажеш окремо в тому чаті.

## 1. Загальна архітектура

**Стек:**
- Бекенд: Node.js + Express, PostgreSQL, JWT-автентифікація
- Фронтенд: чистий HTML/CSS/JavaScript (без фреймворків — React/Vue тощо), кожна сторінка — окремий самодостатній `.html`-файл
- Розгортання: Docker Compose (3 контейнери: `postgres`, `api`, `nginx`), на VPS-хостингу
- Пошта: Nodemailer через SMTP (Gmail App Password або власна поштова скринька)

**Структура папок:**
```
backend/
├── public-site/       # публічний сайт — окремий HTML-файл на сторінку
├── admin-site/        # адмін-панель — один файл index.html (SPA-подібний, перемикання view через JS)
├── error-pages/        # 401/403/404/429/500.html, брендовані
├── src/
│   ├── server.js       # головний Express-застосунок
│   ├── db.js            # пул з'єднань PostgreSQL
│   ├── mailer.js        # відправка листів (заявки + розсилки)
│   ├── migrate.js       # застосування schema.sql
│   ├── create-admin.js  # створення першого адмін-акаунту
│   ├── middleware/auth.js   # requireAuth, requireRole
│   ├── utils/asyncHandler.js # обгортка проти падіння сервера (див. розділ 8)
│   └── routes/           # окремий файл на кожну сутність (див. розділ 4)
├── nginx/nginx.conf     # конфіг проксі — 2 домени (сайт + admin.домен)
├── docker-compose.yml
├── Dockerfile
├── schema.sql            # вся структура бази одним файлом, ідемпотентна
├── package.json
└── .env                  # реальні паролі/ключі (не в git)
```

## 3. Критично важливо: ідемпотентність schema.sql

`schema.sql` виконується щоразу при деплої (`npm run migrate`) — тому кожен `CREATE TABLE` обов'язково з `IF NOT EXISTS`. **Але** якщо пізніше додаєш нову колонку до вже існуючої таблиці, `CREATE TABLE IF NOT EXISTS` її **не додасть** (таблиця вже існує — команда просто ігнорується). Тому кожну нову колонку додавай ще й окремим рядком:

```sql
ALTER TABLE offices ADD COLUMN IF NOT EXISTS map_embed_url TEXT;
```

Це врятує від ситуації "в коді колонка є, а в базі — нема, і все падає з 500-ю помилкою".

## 4. Бекенд — усі API-роути

Базовий шлях: `/api/*`. Патерн для кожної сутності однаковий:
- `GET /` — публічний, без авторизації, тільки опубліковане, фільтр по `?lang=`
- `GET /admin/all` — під авторизацією, все (і чернетки)
- `POST /`, `PATCH /:id`, `DELETE /:id` — під авторизацією (`requireAuth` + `requireRole('admin','content_manager')`)

Роути: `auth` (+ `auth/2fa/*`), `leads`, `vacancies`, `countries`, `reviews`, `articles`, `media`, `users`, `settings`, `social-links`, `offices`, `process-steps`, `team`, `content-blocks`, `licenses`, `faqs`, `subscribers`.

**Особливості:**
- `leads.js` — приймає `multipart/form-data` (через `multer`) для прикріпленого файлу (резюме тощо), і одразу відправляє email-сповіщення менеджеру
- `vacancies.js` — при публікації нової вакансії англійською автоматично шле лист усім активним підписникам (`subscribers`), у фоні, не блокуючи відповідь
- `auth.js` — двоетапний вхід: якщо в юзера увімкнена 2FA, спочатку повертається тимчасовий короткоживучий токен (`stage:'2fa-pending'`, 5 хв), і лише після підтвердження коду видається повний робочий JWT
- `twofa.js` — генерація TOTP-секрету + QR-коду (пакети `otplib` + `qrcode`), підтвердження, вимкнення (з підтвердженням паролем)

## 5. Обов'язкові захисні механізми (набиті ґулі — не повторюй)

### 5.1 Обгортка асинхронних роутів (`asyncHandler`)
Express 4 **не ловить** помилки з `async`-функцій автоматично. Якщо запит до бази впаде з помилкою всередині `async (req,res) => {...}` без обгортки — це стає unhandled promise rejection, і **весь Node-процес може впасти цілком**, а не просто повернути 500. Це проявляється як хаотичні 502-ві помилки то на одній сторінці, то на іншій.

**Рішення:** кожен `router.get/post/patch/delete` обов'язково обгорнутий:
```js
const { asyncHandler } = require('../utils/asyncHandler');
router.get('/', asyncHandler(async (req, res) => { ... }));
```
Плюс страхувальна сітка в `server.js`:
```js
process.on('unhandledRejection', (reason) => { console.error(...); });
process.on('uncaughtException', (err) => { console.error(...); });
```

### 5.2 Вимкнене кешування API-відповідей
Express за замовчуванням додає ETag до JSON-відповідей. Браузер починає кешувати навіть дуже "живі" дані (вакансії, налаштування) — і зміни, зроблені в адмінці, не з'являються на сайті доти, доки не мине кеш. Симптом: "щось показується на секунду і зникає" або "зміни не застосовуються".

**Рішення в `server.js`:**
```js
app.disable('etag');
app.use('/api', (req, res, next) => {
  res.set('Cache-Control', 'no-store, no-cache, must-revalidate, private');
  next();
});
```
(зверни увагу — застосовується тільки до `/api`, не до `/uploads` — картинки кешувати можна й треба)

### 5.3 Nginx мусить проксіювати `/uploads/`
Якщо забути цей блок — усе, завантажене через адмінку (лого, фото, обкладинки), фізично не відкриється на сайті (404), хоча в базі посилання буде правильне.
```nginx
location /uploads/ {
  proxy_pass http://api:4000/uploads/;
  proxy_set_header Host $host;
}
```
Потрібно в **обох** серверних блоках nginx.conf — і для основного домену, і для `admin.домен`.

### 5.4 Міграція — окремі команди, не один блок
Якщо `migrate.js` виконує весь `schema.sql` одним запитом (`pool.query(fullText)`), і десь посередині файлу команда падає — **все, що після неї, теж не виконається** (транзакція відкочується), без чіткого повідомлення про те, яка саме команда винна.

**Рішення:** розбивати файл на окремі SQL-команди (по `;`, з урахуванням `DO $$ ... $$;` блоків) і виконувати кожну окремо в циклі, з логом успіху/провалу для кожної.

### 5.5 Права доступу після `scp`
Файли, скопійовані з Windows через `scp`, часто отримують занадто закриті права — Nginx у контейнері (інший користувач) не може їх прочитати → 403 на всьому сайті. Після кожного розгортання:
```bash
chmod 755 /opt /opt/<project> /opt/<project>/backend
find /opt/<project>/backend/public-site -type d -exec chmod 755 {} \;
find /opt/<project>/backend/public-site -type f -exec chmod 644 {} \;
```
(і так само для `admin-site`, `error-pages`)

## 6. Патерн "динамічний контент зі статичним резервом"

Кожна публічна сторінка спершу рендериться зі **статичним прикладом даних прямо в HTML** (щоб сторінка ніколи не була порожньою, навіть якщо JS/API не спрацює), а потім JS підвантажує реальні дані з API і **замінює** статичний вміст, якщо відповідь непорожня:

```js
async function loadXFromApi(lang){
  try {
    const res = await fetch(API_BASE + '/x?lang=' + lang);
    if (!res.ok) return;              // тихо лишаємо статичний резерв
    const items = await res.json();
    if (!items.length) return;         // те саме
    // ... замінюємо DOM реальними даними
  } catch (err) { }
}
```

Це і швидший перший рендер (не чекаємо API), і захист від "порожнього сайту", якщо бекенд тимчасово недоступний.

**Важливо:** одразу засівай базу (`seed.sql`) тими самими даними, що вже "зашиті" в статичний HTML, **на всіх мовах** — інакше нова мова на сайті буде показувати порожньо, поки хтось не зайде і не заповнить вручну.

## 7. Адмін-панель — повний перелік розділів

Дашборд (реальні цифри — нові заявки, активні вакансії, останні заявки) → Заявки (CRM зі статусами new/in_progress/processed, пошук, фільтр) → Вакансії → Країни → Відгуки → Блог (з обкладинкою) → Офіси (фото АБО Google Maps) → Етапи процесу → Команда → Текст "Про нас" (+ статистика) → Ліцензії/нагороди → FAQ → Сховище файлів (пошук/фільтр/сортування, зображення+документи) → Підписники (+ CSV-експорт) → Користувачі (ролі) → Налаштування (контакти, месенджери, соцмережі, лого, 2FA).

**Ключові UX-деталі, варто повторити:**
- Кожна мультимовна сутність редагується в одній модалці з мовними вкладками (EN/DE/RO/RU чи які потрібні), одна кнопка "Зберегти" створює/оновлює всі заповнені мови одночасно
- Обов'язкові поля підсвічуються червоним при спробі зберегти без них
- Кнопки збереження показують спінер і блокуються на час запиту (`try/finally` — розблокування гарантоване навіть при помилці)
- Ролі: `admin` (все), `content_manager` (контент, без користувачів), `leads_manager` (тільки заявки+підписники) — бічне меню й доступ до view фільтруються по ролі на фронті, **і додатково** перевіряються на бекенді (`requireRole`) — ніколи не покладайся тільки на приховування кнопки в UI
- "Запам'ятати мене" — токен у `localStorage`, з перевіркою дійсності при відкритті сторінки (пробний запит; якщо 401 — тихо просить увійти знову)

## 9. Форми — обов'язкові правила

- Кожна форма: ім'я обов'язкове, і **або** телефон **або** email (не обидва одразу обов'язкові)

- Кожна форма посилається на `privacy-policy.html`

## 11. Розгортання на хостингу (HostPro VPS, Docker без панелі керування)

1. Домен → DNS ("Керування DNS" в HostPro після переходу на власні name-сервери) → A-записи: `@`, `www`, `admin` → IP сервера
2. SSH на сервер, встановити Docker, ufw, fail2ban
3. `scp -r backend/* root@IP:/opt/<project>/backend/`
4. Заповнити `.env` (реальні паролі бази, JWT_SECRET, SMTP)
5. `certbot certonly --standalone` для обох доменів (основний + `admin.`)
6. `docker compose up -d --build`
7. `docker compose exec api npm run migrate`
8. `docker compose exec api node src/create-admin.js` — перший адмін-акаунт
9. Права доступу (розділ 5.5)
10. Якщо є seed-файл з демо-контентом: `docker cp seed.sql $(docker compose ps -q postgres):/tmp/ && docker compose exec postgres psql -U user -d db -f /tmp/seed.sql`

**Для нового домену на тому самому сервері:** окрема папка `/opt/<новий-проєкт>/`, окремий `docker-compose.yml` з іншими портами (postgres/api не повинні конфліктувати з портами існуючого проєкту — приміром `4001:4000` замість `4000:4000`), спільний Nginx-контейнер отримує ще один `server{}`-блок для нового домену, окремий сертифікат через certbot.
